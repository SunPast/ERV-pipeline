# Common issues (all actually encountered)

## 1. Telescope reports `fetch called on bamfile without index`

**Cause**: `telescope assign --ncpu > 1` uses the parallel loader, which internally calls `pysam.fetch(region)` and therefore requires a BAM index;
but Telescope requires its input to be a **collated BAM** (same read pair adjacent), and such files **cannot be indexed**:

```
samtools index collated.bam
[E::hts_idx_push] Chromosome blocks not continuous
```

**Correct approach**: `--ncpu 1`. The single-threaded path uses `until_eof` streaming and does not need an index.
Put parallelism into "concurrent samples", consistent with the full rerun in 2026-10 (42 samples in parallel, about 33 minutes per sample).

## 2. `samtools collate -n` does not mean "sort by name"

In samtools 1.18:

- `-n INT` = number of temporary files (default 64)
- It does not mean "sort by read name"

Writing `-n -l 6` makes `-l` the value of `-n`, and then `6` is treated as an input file, causing `Cannot open input file "6"`.

Correct form: `samtools collate -@ 8 -n 8 -l 6 -o out.bam in.bam`.

## 3. Telescope defaults to `--attribute locus`

Without an explicit setting, it takes the feature name from the GTF's `locus` attribute.
The locus GTF generated by this project writes both `gene_id` and `locus` (identical), but the script still passes `--attribute gene_id` explicitly, to avoid silent breakage if the GTF changes later.

## 4. Column 6 of `ERVmap.bed` is all `+`

This is not something we lost; the source file is like that. When the real strand is needed, read the ERV layer of
`ERV-data/rerun_out/supplement_subfamily_locus/final/locus_catalog.csv`.

## 5. SQuIRE does not accept external annotation

0.9.9.92 only has `squire Build` (auto-downloads rmsk from UCSC), there is no `MakeBed`.
Hence its annotation differs from the unified reference by about 3.2% of loci; subfamily-level comparison is unaffected.

## 6. TEcount index construction is extremely slow at 720k loci

`TEcount` is the "single-sample counting" tool in the TEtranscripts package (TEtranscripts itself requires `-t` and `-c` as a pair and cannot be used per sample).

Measured: with the 720,871-row exon GTF, a single sample takes **87 minutes** in total, with peak memory 2.59 GB; most of the time is spent in `Building TE index`.
The same gene GTF (1.3M rows) took about 7.5 minutes to build the gene index; the TE index is clearly slower, presumably because intervals are built element by element.

**Suggested handling**:

1. First confirm whether this is acceptable: 1.45 core-hours per sample, about **6,200 core-hours** for 4,288 samples. Note that the index build is independent of the sample but is rebuilt for every sample, which is the main waste;
2. If not acceptable, switch to `featureCounts -M --fraction -O -t exon -g gene_id` (subread) for locus-level counting,
   whose "distribute multi-mapping proportionally" semantics match TEtranscripts; it runs in minutes. This repository does not include it yet, to avoid introducing an unverified dependency.

**Note**: whichever backend is used, summing locus level back to subfamily will differ from the existing subfamily-level results by a few percent; this is the inevitable consequence of finer granularity.
